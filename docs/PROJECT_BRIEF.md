# DocsGPT: reliable developer support

## Goal

Develop a demonstrably reliable FastAPI documentation and GitHub issue
assistant suitable for an AI Engineer / AI SDE portfolio. Explain engineering
decisions clearly, record actual measurements, and distinguish implemented
features from validated outcomes.

Repository: https://github.com/aakashpatil14/docsgpt

## First reliability update

- Assign one citation ID per URL before prompting, preserving the same IDs in
  the API and UI even when several chunks come from the same document.
- Return an explicit unknown answer without an LLM call when there are no
  citable chunks.
- Validate question length, whitespace-only input, and retrieval strategies.
- Expire in-memory cache entries and version answer keys by corpus, prompt,
  model backend, and retrieval configuration.
- Run deterministic generation/API/cache regressions in ordinary PR CI.

Citation mapping is not semantic citation verification. An LLM can still make
an unsupported statement or invent a marker. Evaluate these separately.

## Next milestone: measured evaluation

1. Assemble 60 reviewed cases: 20 documentation questions, 15 troubleshooting
   questions supported by issue discussions, 10 version-sensitive questions,
   5 multi-source questions, and 10 ambiguous or unanswerable questions.
2. Label each case with exact supporting URLs and passages, a reference answer
   or expected abstention/clarification, and the relevant software versions.
   Verify source labels against a fixed corpus snapshot before scoring.
3. Keep 20 cases held out; use the remaining 40 for development. Do not tune
   against the held-out cases. Report answerable and unanswerable results
   separately rather than assigning retrieval failures to unanswerable cases.
4. Compare vector, hybrid, and hybrid + reranking on the same corpus and model
   settings. Record Hit@5, MRR, citation support, abstention behaviour, p50/p95
   latency, and model token usage/cost where available. Separate cached and
   uncached timing. Repeat timing measurements and record sample counts.
5. Commit reproducible result artifacts and failure analysis. Replace README
   TBD values only with actual measurements. Record model versions, corpus
   revision, date, hardware, and configuration with results.

Current small datasets are smoke tests, not proof of general quality. Live
benchmarks require an ingested corpus and configured model services. No live
benchmark numbers or deployment claims were generated by this update.

## Subsequent milestones

- Include issue comments and distinguish suggested fixes from confirmed
  resolutions; preserve URLs, versions, timestamps, and source provenance.
- Refresh documentation and incrementally re-embed changed content, remove
  superseded chunks, and automate corpus-version publication after success.
- Build one troubleshooting workflow: error + version + code sample →
  clarification if needed → retrieval → sourced explanation → suggested fix
  and verification test. Measure improvement before adding tool routing.
- Add database pooling, timeouts, background ingestion, and load testing.
- Deploy a verified demo, collect feedback from 3–5 developers, and record a
  two-minute walkthrough with architecture, real results, and limitations.
